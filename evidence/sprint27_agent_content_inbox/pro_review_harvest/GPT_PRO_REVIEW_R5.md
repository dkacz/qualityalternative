FRESH FINDINGS:

HIGH — Duplicate prevention is authoritative, but not atomic, and import-time duplicate discovery does not produce a finite duplicate review state.
Exact claim: Two Agent Inbox packages with the same verified content bytes but different Drive package folders can both be READY after a scan when the fingerprint was not already present in the local library; the import path then performs findDocumentByFingerprintSha256(contentSha256) before writing, but that lookup and the later insert are not protected by a fingerprint-level transaction or unique constraint. Under concurrent import attempts, both imports can pass the lookup and insert distinct document rows because the Room uniqueness constraint is on uri, not documentFingerprintSha256. In the sequential case, the second import is correctly returned as DUPLICATE, but MainViewModel leaves the candidate in its prior READY state rather than converting it to a finite duplicate/removable review item.
Why it is vulnerable: This is a concrete user data-integrity and release-gate attack against the known duplicate-private-document bug class. A user-controlled Drive inbox can contain two same-byte packages; an automated touch race, rapid UI interaction, duplicated authorization callback, or direct ViewModel re-entry can start two imports before either write is visible to the DAO lookup. Because the stored URI includes the package folder id and verified SHA, two same-SHA packages from different folders have different URIs, so OnConflictStrategy.REPLACE on uri does not prevent two private documents. Even without the race, same-scan duplicate packages remain visually importable after the authoritative duplicate result, which contradicts the PRD requirement that duplicated packages be visible as finite review items rather than misleading ready candidates.
